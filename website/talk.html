Some background on swiyu

The issue

Various services need to verify certain claims about a user (over 18, licensed, is a real person) to operate. The only way to achieve this right now is to hand over a full credential, like a scan of a physical ID, to the service.

  1. Mar 2021

    Voters rejected a plan for a privately issued e-ID.

  2. Sept 2025

    State-issued e-ID and swiyu was approved.

  3. 2027

    Planned launch of the swiyu ecosystem after some delays.

Sources: e-ID technology; 28 Sept 2025 vote

Selective disclosure JWT tokens

swiyu Wallet (app) keeps the credential and lets the holder disclose specific fields using an SD-JWT (RFC 9901). The main privacy point is that the actual claims leave the signed payload (replaced by salted hashes) and can be selectively disclosed when needed.

JWT token

{
  "iss": "did:tdw:…",
  "vct": "beta-id",
  "birthdate": "2001-05-03",
  "family_name": "Meier",
  "cnf": { "jwk": { "kty": "EC", … } }
}
+ ES256 signature
(no disclosures)
→

SD-JWT

{
  "iss": "did:tdw:…",
  "vct": "beta-id",
  "_sd": [
    "H(s₁ ‖ birthdate ‖ 2001-05-03)",
    "H(s₂ ‖ family_name ‖ Meier)"
  ],
  "cnf": { "jwk": { "kty": "EC", … } }
}
+ ES256 signature
[s₁, "birthdate", "2001-05-03"]
[s₂, "family_name", "Meier"]
+ kb+jwt (proves cnf.jwk)

Unlinkability

A disclosed claim can still be correlated, and so can the holder device key in cnf. Presentations that cannot be tied back to a person need ZK, which swiyu does not do yet.

Sources: RFC 9901; swiyu Technology Stack

Swiyu infrastructure

fedpol, FEDRO, the cantons, and later companies issue e-ID, driver licenses, and others through the Generic Issuer.
The holder uses swiyu Wallet (app) and receives the issued credentials.
The verifier can use swiyu Check (in person) and the Generic Verifier (online) to query then check the disclosures from the wallet.

Sources: swiyu Introduction; Technology Stack; Open Source Components; Generic Verifier

How does swiyu deal with linkability?

To solve the linkability of individual SD-JWT presentations, swiyu instead issues a batch of easily renewable credentials at once.

Sources: How to make the e-ID unlinkable; Batch issuance whitepaper; Swiss Profile Issuance

Why ZK?

Batch issuance misses:

  • Predicate proofs over the claims
  • Protection against colluding verifiers (and issuers) who can correlate disclosed claims / holder keys

How ZK?

  • A lot of mismatched backends: Crescent, Longfellow, etc.
  • OpenAC / zkID: proves the ES256 SD-JWT swiyu already issues; Prepare once, then a cheap Show per presentation. (Ran zkao and shared PoCs.)
  • EPFL + SICPA: Noir with a custom Spartan backend, built for proving speed. (Shadowed and audit.)
  • Mombelli (ETH): general-purpose Circom circuits, including constraints across linked credentials.
  • and others... (more funding is being allocated for this as well)

Sources: OpenAC / zkID; EPFL + SICPA Spartan backend; Mombelli thesis

Circuits on OpenAC

I used OpenAC's Prepare/Show suite to write four predicates on swiyu SD-JWTs.

Over 18 + status

Issuer authentication, holder key, credential validity, private Token Status List, and a hidden birthdate cutoff.

Canton allow-list

Private resident_canton against a verifier-chosen list of up to four cantons.

Residence

Municipality / residence eligibility, including combined disclosure.

One claim

One accepted presentation per credential and verifier scope (nullifier).

A generic integration layer

We worked on a proof-system-agnostic overlay on the OID4 protocols swiyu already runs. Issuance still uses OID4VCI while ZK presentations use a fork of OID4VP and DCQL with small additions.

  • Extending DCQL: The Generic Verifier puts x_swiyu_zkp on a DCQL query in the signed request object. The wallet returns an opaque proof in vp_token through the usual direct_post.
  • Using one process contract: All adapters would use swiyu.provider.v1 (prepare, present, verify) and would just be backends running the proofs and verification steps.
  • Declaring claims: a versioned JSON claim lists the attributes, assertions, and predicates a presentation must establish, so two adapters can implement the "same thing" (for example age at least 25 plus a holder challenge) even if they use very different proof systems or stacks.
