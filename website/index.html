Issuer

swiyu-issuer creates credential offers, authorizes issuance, signs credentials, and publishes or updates status information.

Vocabulary

OID4VCIOpenID for Verifiable Credential Issuance
The protocol between an issuer and a wallet. It covers discovering issuer metadata, accepting a credential offer, obtaining authorization, proving possession of a holder key, and downloading the signed credential.
Technical details and example issuance exchange

OID4VCI separates business authorization from credential delivery. A credential offer identifies what may be issued; an OAuth access token authorizes collection; a credential request proves that the wallet controls the key that should be bound into the credential.

  1. The wallet follows a credential offer and reads issuer metadata.
  2. It exchanges an authorization code or pre-authorized code at the token endpoint.
  3. It obtains a fresh credential nonce and creates a holder proof JWT.
  4. It calls the credential endpoint with the access token, DPoP proof when enabled, requested format and holder proof.
  5. The issuer validates the request, signs the credential and returns it immediately or through deferred issuance.

Schematic request

POST /oid4vci/api/credential
Authorization: DPoP eyJ...
DPoP: eyJ...
Content-Type: application/json

{
  "format": "dc+sd-jwt",
  "proof": {
    "proof_type": "jwt",
    "jwt": "eyJ..."
  }
}

Security binding: the holder proof and DPoP serve different layers. The credential proof binds the credential to a holder key; DPoP binds OAuth requests/tokens to the client key used for those HTTP calls.

OID4VPOpenID for Verifiable Presentations
The protocol between a verifier and a wallet. The verifier sends a request describing what it needs; the wallet returns one or more credential presentations to a response endpoint.
Technical details and example presentation exchange

The verifier first creates server-side session state. The wallet receives a signed authorization request containing a nonce, client identifier, response URI and DCQL query. The nonce prevents replay; state correlates the browser/protocol round trip with the persisted session.

Wallet fetches the signed request

state=Zk2...
vp_token={"identity":["eyJ..."]}

In this verifier: VerificationController decrypts the response when needed, checks the OAuth state, maps the form into a typed presentation result, and then hands DCQL processing to PresentationVerificationUsecase.

DCQLDigital Credentials Query Language
A structured query carried inside OID4VP. It gives requested credentials IDs, acceptable formats and credential types, requested claims, and constraints. The wallet response maps those query IDs to values in vp_token.
Technical details and example query

Each entry in credentials has an id. That ID is the join key between the verifier’s request and the wallet’s vp_token map. The verifier never has to guess which returned token answers which query.

{
  "credentials": [{
    "id": "age",
    "format": "dc+sd-jwt",
    "meta": {
      "vct_values": ["https://example.ch/identity"]
    },
    "claims": [{
      "id": "birthdate",
      "path": ["birthdate"]
    }],
    "require_cryptographic_holder_binding": true,
    "x_swiyu_zkp": {
      "profile": "swiyu-age18-status-2k-v0",
      "circuit_id": "swiyu_age18_status_2k",
      "cutoff_date": "2008-08-17",
      "status_list_snapshot": "statuslist-jwt:AbC...",
      "current_time": 1786939200
    }
  }]
}

The corresponding response is conceptually {"age":["<proof envelope>"]}. The local validator further requires one credential, one birthdate claim, no requested disclosed value, one presentation and the exact supported ZK profile.

SD-JWT VCSelective Disclosure JWT Credential
A JWT-based credential whose issuer signature commits to hidden claims through digests. The holder can reveal chosen claim disclosures. Selective disclosure alone is different from proving a predicate such as “over 18” without revealing the birthdate.
Technical details and disclosure example

The issuer removes a selectively disclosable claim from the signed payload and replaces it with a digest in _sd. The holder receives the signed issuer JWT plus the original disclosure. At presentation time, the holder appends only the disclosures it wants to reveal.

Signed payload fragment

{
  "iss": "did:tdw:issuer...",
  "vct": "https://example.ch/identity",
  "_sd_alg": "sha-256",
  "_sd": ["B7M_t4...ZxQ"],
  "cnf": {"jwk": {"kty":"EC", ...}}
}

Disclosure before base64url encoding

[
  "random-salt",
  "birthdate",
  "2000-01-15"
]

presentation =
  issuerJWT~disclosure~keyBindingJWT

The verifier hashes the exact encoded disclosure and checks that its digest appears in the signed _sd array. The ZK circuit goes further: it authenticates that disclosure but keeps its value private while comparing the birthdate with a public cutoff.

DPoPDemonstrating Proof of Possession
An OAuth mechanism that binds requests and access tokens to a client-held key. The issuer uses it to reduce the value of a stolen bearer token.
Technical details and proof JWT example

A DPoP proof is a short-lived JWT signed by the client key. The protected header carries the public JWK. The payload binds the signature to one HTTP method and target URI; jti and iat help detect replay. A resource request may also include ath, a hash of the access token.

header = {
  "typ": "dpop+jwt",
  "alg": "ES256",
  "jwk": {"kty":"EC","crv":"P-256","x":"...","y":"..."}
}

payload = {
  "jti": "9d2...",
  "htm": "POST",
  "htu": "https://issuer.example/oid4vci/api/credential",
  "iat": 1786939200,
  "nonce": "issuer-provided-nonce",
  "ath": "base64url(sha256(access_token))"
}

The issuer recomputes the expected method, URI and token hash, verifies the signature, and checks that the token is bound to the same JWK thumbprint.

Request object / JARSigned authorization request
The verifier serializes its OID4VP request as a signed JWT. The signature protects the nonce, audience, response URI, DCQL query, and, on the ZK path, the proof policy.
Technical details and signed-claims example

The request object is a JWS: base64url(header).base64url(claims).signature. The verifier signs the complete authorization request so a relay or wallet-facing frontend cannot silently weaken the requested credential or replace the ZK cutoff/snapshot.

{
  "iss": "did:tdw:verifier...",
  "aud": "https://self-issued.me/v2",
  "client_id": "x509_san_dns:verifier.example",
  "response_uri": "https://verifier.example/.../response-data",
  "response_type": "vp_token",
  "response_mode": "direct_post",
  "nonce": "fresh-verification-nonce",
  "state": "opaque-session-correlation",
  "dcql_query": {"credentials": [...]}
}

In the local implementation, x_swiyu_zkp lives inside one DCQL credential object. Because the existing request-object serializer copies the DCQL query into the signed JWT, no second policy transport or endpoint is needed.

zkID proof stackCircom → R1CS → witness → Spartan2 / Hyrax
The complete proving toolchain used by the local profiles. Circom defines the statement, witness code fills its signals, Spartan2 proves the resulting constraints, and Hyrax supplies the commitment layer used by that proof system.
Technical details and complete artifact lifecycle
  1. Author in Circom. Templates constrain SD-JWT parsing, issuer and holder signatures, validity windows, private claims, status membership, and the requested predicate.
  2. Compile once per circuit shape. Circom emits an .r1cs constraint system, a WASM witness generator, and a .sym signal map. R1CS is a matrix representation of equations of the form A · B = C.
  3. Generate a witness. TypeScript assembles authenticated credential and verifier inputs. Browser builds run the generated WASM; native builds use witnesscalc_adapter. Both produce the ordered field assignments stored as .wtns data.
  4. Preprocess the fixed circuit. Rust loads the R1CS through circom-scotia and calls R1CSSNARK::setup. This circuit-specific step creates the proving and verifying keys once for that exact relation.
  5. Prove a private assignment. The prover supplies the proving key, witness, and public values to Spartan2. The selected T256HyraxEngine uses Hyrax polynomial commitments inside the Spartan2 R1CS proof.
  6. Verify the exact statement. The verifier supplies the verifying key, proof, and independently reconstructed public values. The proof is accepted only when Spartan2 verifies and those values exactly match the signed verifier session.

Build-time artifacts

profile.circom
  ├─ profile.r1cs   fixed equations
  ├─ profile.wasm   witness calculator
  └─ profile.sym    signal positions

R1CSSNARK::setup(shape)
  ├─ proving key    held by prover
  └─ verifying key  held by verifier

Per credential and presentation

private credential + public policy
  → witness generator
  → ordered witness (.wtns)
  → Spartan2 prover + proving key
  → proof + public values
  → Spartan2 verifier + verifying key
  → accept or reject

Spartan2 is the proof protocol that establishes satisfaction of the compiled R1CS. Hyrax is the polynomial commitment scheme selected by this implementation’s engine, allowing the prover to commit to witness-derived data while the verifier checks the proof without receiving the private assignments.

Prepare and Show: the optimized profiles preprocess and authenticate credential data in a reusable Prepare proof, then create a smaller session-bound Show proof. Reblinded shared-witness commitments require both proofs to refer to the same hidden credential values without exposing them.

ZK sidecarLocal verifier helper
A separate local process used because the Java verifier does not directly run the TypeScript/WASM/Rust proof stack. Java sends the proof plus authoritative expected context over an explicit loopback-only HTTP endpoint.
Technical details and sidecar API example

Java → sidecar

POST http://127.0.0.1:7788/v1/verify

{
  "proof_envelope": "<opaque wallet output>",
  "expected": {
    "nonce": "...",
    "client_id": "...",
    "response_uri": "...",
    "state": "...",
    "query_id": "age",
    "profile": "swiyu-age18-status-2k-v0",
    "cutoff_date": "2008-08-17",
    "status_list_snapshot": "statuslist-jwt:AbC..."
  }
}

Sidecar → Java

{
  "verified": true,
  "profile": "swiyu-age18-status-2k-v0",
  "circuit_id": "swiyu_age18_status_2k",
  "predicate_satisfied": true,
  "status_valid": true,
  "status_list_snapshot": "statuslist-jwt:AbC..."
}

The sidecar resolves the issuer key and trust policy, resolves the configured signed status snapshot locally, recomputes the challenge/public inputs, and calls the Spartan verifier. Java uses strict JSON parsing and rechecks exact profile, circuit and snapshot equality.

Fail-closed behavior: no endpoint, non-loopback URI, timeout, non-200 response, oversized body, malformed JSON or verified != true rejects the ZK presentation. It does not fall back to ordinary SD-JWT verification.

ZK implementation

Four experiment statements

Age: the signed private birthdate satisfies the verifier cutoff. Canton: the signed private canton belongs to the verifier’s accepted set. Residence: the signed private municipality belongs to an accepted set and the residence start date satisfies a duration threshold. One claim: the exact issuer-authenticated credential attestation has not already been accepted in the canonical verifier scope. Every profile also binds holder possession, credential validity, the verifier session, and a VALID status entry.

1. Verifier request model

  • ZkPresentationPolicyDto adds x_swiyu_zkp to one DCQL credential query.
  • The policy names the exact profile, circuit, age cutoff, status snapshot and evaluation time.
  • CreateVerificationManagementValidator accepts only dc+sd-jwt, one presentation, holder binding, and exactly one undisclosed birthdate claim.
  • The policy is persisted with dcql_query and therefore covered by the normal signed OID4VP request object.

2. Verifier-side routing

  • DcqlMapper maps the vendor extension into the domain ZkPresentationPolicy.
  • DcqlPresentationVerificationService detects that policy and requires exactly one proof envelope for the query ID.
  • Ordinary queries still use PresentationVerifier; ZK queries use ZkPresentationVerifier.
  • The result is reduced to profile, circuit, predicate result, status result and snapshot ID.

3. Authoritative sidecar boundary

  • HttpZkPresentationVerifier builds ExpectedContext from persisted verifier state: nonce, client ID, response URI, OAuth state, query ID, policy, VCT, accepted issuer DIDs and trust anchors.
  • It accepts only an explicit loopback HTTP endpoint, disables redirects, bounds response size and fails closed on timeout or malformed output.
  • The sidecar resolves the issuer/trust policy and a locally provisioned signed status-list snapshot; it does not trust envelope lookup hints.
  • The Java service independently checks returned profile, circuit, snapshot, predicate and status equality.

4. Wallet prepare → provision → show API

  • prepareSwiyuCredential parses and authenticates the fixed Swiss SD-JWT shape.
  • provisionSwiyuCredentialStatus verifies a locally fetched statuslist+jwt and derives the Merkle witness for the credential’s signed private index.
  • SwiyuZkpWallet.show binds the verifier challenge, cutoff, time and snapshot, checks validity, asks the holder key to sign the challenge digest, generates the witness and produces one proof.
  • show performs no network lookup; its credential and status inputs were already authenticated.

5. Fixed Circom relation

  • SwiyuAge18Status verifies the issuer ES256 signature, protected header profile, signed registered claims and exact top-level disclosure membership.
  • It proves the hidden ISO birthdate is at or before cutoff_date, verifies the holder P-256 signature, and enforces nbf ≤ current_time < exp.
  • A fixed-depth SHA-256 Merkle path proves the signed private status index has two-bit value VALID.
  • Credential bytes, disclosure, holder key, status URI/index and Merkle branch stay private; the verifier-selected context is public.

6. Spartan2 proof backend

  • Circom compiles the relation to R1CS; SwiyuCircuit exposes the fixed public-value layout.
  • prove_swiyu_from_witness generates one Spartan2 proof.
  • verify_swiyu requires the proof, verifying key and all ten expected public values. Proof bytes alone cannot choose the statement being verified.
  • The SDK supports WASM bindings, but the working full-profile path uses the Node/native backend with local-file key references.
