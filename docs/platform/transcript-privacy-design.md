# Claim-derived transcript privacy testing

A provider can verify a zero-knowledge proof successfully while its integration discloses private data in an HTTP header, wrapper field, error, or extra request. The harness tests that integration boundary by comparing complete selected flows for credentials with the same permitted meaning.

## Contribution

The contribution is a reusable connection between a pinned semantic claim, its approved release policy, actual provider execution, and a privacy test over the observer's protocol transcript. Provider contributors supply fixture construction and the provider interface. The harness owns semantic classification, transcript capture, comparison rules, and the report.

This is an engineering contribution, not a claim to have invented relational security testing. [Metamorphic Testing for Web System Security](https://arxiv.org/abs/2208.09505) already uses relations among executions to test web security. [OpenID4VP 1.0](https://openid.net/specs/openid-4-verifiable-presentations-1_0.html) specifies session binding and privacy requirements. Here the practical focus is preserving the submitted ZK statement's declared disclosure boundary through a Swiyu integration. A broader literature review would be needed to claim priority over all related systems.

## Property

For an approved claim C, public verifier inputs g, and release policy R, choose private fixtures w₁ and w₂ such that:

- Their credentials authenticate against the supplied issuer.
- Their predicates have the same outcome and their permitted released values agree.
- Their verifier inputs agree, allowing only declared fresh session values to be renamed.
- Their observed verifier outcomes agree with the expected outcome.

Execute the same selected flow with both fixtures. The observer's transcript projections should agree after validating and renaming permitted fresh values and replacing only declared cryptographic byte fields with their observable representation and length. In compact notation:

`same permitted meaning(C, R, g, w₁, w₂) ⇒ equivalent observed flows(T₁, T₂)`

A difference is a counterexample to this declared relation for the selected observer and flow. An unexpected rejection is retained as a functional finding. A pair whose public meaning differs is ineligible for that relation; it does not count as a passing comparison.

The independent classifier authenticates the SD-JWT and checks supported metadata, validity, and predicate rules. The native holder and status relations are checked by the actual submitted verifier. The generic reference status tree differs from OpenAC's native circuit, so the harness does not pretend to independently re-prove those native assertions. Reports expose this distinction.

## Observer and normalization contract

Capture complete application-level HTTP exchanges for the selected flow, including headers, endpoints, status codes, message order, and bodies. Decode transport wrappers before comparison: form data, JSON, compact JWT, and base64url JSON. Keep unknown sibling fields and repeated form parameters. An adapter must not replace the transcript with a hand-picked list of fields it wishes to disclose.

Normalization is an explicit part of the experiment:

- A nonce or state is replaced only after checking its actual value against the session value generated by the harness. Preserve its use across messages.
- Keep verifier identity, policy, status snapshot, query identifiers, and permitted disclosure values comparable.
- An opaque proof exemption applies to a specific scalar field, not its parent envelope. Proof length stays visible. Extra siblings remain observable.
- Search for private fixture markers before opaque-field replacement. This catches direct disclosure even if all sessions leak the same value.
- Compare all remaining values, including unknown hashes. This catches differences that a marker scanner cannot recognize.
- A single valid response Date header and the request-object absolute issuance time are explicit unassessed clock channels. For the signed request object, preserve `exp - iat` so a changed validity period remains observable. Preserve other payload fields and reject malformed clocks.
- Compact JWS signatures are compared by algorithm and canonical length; the transcript comparator does not verify them.
- Missing captures, unsupported codecs, invalid policies, and decoding limits are coverage failures, not clean results.

A capture is complete only for its named boundaries. A selected OID4VP HTTP flow does not imply coverage of Android UI, every wallet network request, DNS, TLS records, browser extensions, live status registries, or arbitrary process logs.

## Concrete regression experiment

Use real OpenAC proofs for two valid credentials that differ in hidden data while satisfying the same fixed claim. First execute the clean selected Swiyu flow. Then exercise a deliberately faulty integration that adds a credential-derived correlation tag outside the opaque proof.

The decisive result is an accepted presentation with a transcript distinction attributable to hidden data. A digest tag is useful because it need not contain any recognizable private marker: byte comparison should still expose it. A raw-disclosure regression additionally validates decoding and marker scanning.

The report must distinguish an observed defect in unchanged code from a deliberate injected regression. Both are useful evidence, but they support different conclusions. No finding in the clean run establishes only that these cases did not falsify this relation.

## Limits

Finite tests cannot establish computational indistinguishability or cryptographic zero knowledge. Masking proof bytes assumes that audited cryptography provides their intended confidentiality; it cannot test that assumption. Circuit soundness and whether a circuit proves its full claimed relation remain audit obligations.

A few runs give benchmark observations, not a timing-leakage conclusion. Distributional testing needs enough interleaved samples, explicit public covariates, and an appropriate statistical method. Stable-identifier and cross-verifier tests additionally need multiple subjects and scopes. Neither should be claimed from one pair of credentials.

When two approved implementations register the same claim, the same relation is applied across backends. Implementation identity (`x_swiyu_zkp.profile`, `circuit_id`, EPFL issuer coordinates, proof length, and message size) is an explicit exemption. Extra siblings, hidden fixture markers, and unknown identifiers are not. The default `shared-claim-run` starts a Java OID4VP harness per backend. EPFL presents native UltraHonk proofs. OpenAC age-25 presents a session-bound synthetic envelope until Spartan keys exist; that is not cryptographic ZK evidence. See `zkbench.py shared-claim-run` and [the provider guide](../../integration/harness/TRANSCRIPT-PROVIDERS.md#shared-claim-two-circuits).

The completed native experiment and exact runtime boundary are recorded in [the findings](transcript-privacy-findings.md).
